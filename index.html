CLASP: Clustered LoRA Adapter Stacking for Secure and Personalized Code Generation

W = Wbase + α·ΔWcluster + β·ΔWclient

An on-premise federated code-generation system. Each developer's model is composed from a frozen base model, a cluster adapter learned jointly by clients whose code is alike, and a personal adapter. No source code leaves local infrastructure.

GitHub repository Run the demo

Problem statement

Cloud assistants need your code

Hosted code assistants learn a project's context by sending its source off-site. Many organizations cannot allow proprietary code to leave their network.

Local models learn alone

Fine-tuning one model per developer keeps code private, but what one engineer's files teach the model never reaches a colleague on the same project.

Federated LoRA is not plug-and-play

Averaging LoRA factors separately does not average the updates they represent, and a system that keeps producing adapters needs a safe way to decide which one is served and to undo a bad one.

Objectives

Personalize code completion to both the project and the individual developer, with all training on local machines.

Share project knowledge across a team through federated aggregation of LoRA adapters, with differential privacy and mutual TLS on the channels.

Version every adapter immutably, promote only candidates that improve in-project quality without regressing general coding ability, and roll back otherwise.

Methodology: one federated round

A

Edge trains and uploads

Each client trains a rank-16 LoRA (q/k/v/o, 24 layers) on its own repository over a 4-bit base model with the FedProx proximal term, then uploads it to POST /uploads. The personal adapter is trained on the frozen base plus cluster layer, not on the bare base.
B

Cluster aggregates exactly

The server averages the clients' products B·A weighted by sample count, then re-factorizes to rank 16 by truncated SVD computed through thin QR, so the dense update is never formed. The result is published to the registry. Rounds 1–2 use the two project clusters; from round 3, clients are re-clustered by k-means (k = 2) on the cosine similarity of their updates, with static assignment as the fallback.
C1

Registry serves the active version

Immutable, sha256-verified safetensors versions with an active pointer. On promotion the registry stores one pre-merged composite (α·cluster + β·client) per developer, and the edge serves that single adapter on the 4-bit base.
C2

Two-sided promotion

Promote only if in-project completion improves beyond the noise band and HumanEval pass@1 drops by at most 2 points; otherwise roll back. Every decision goes to an audit trail.

Stack: DeepSeek-Coder · PyTorch · PEFT · bitsandbytes (NF4) · Flower · FedProx · Opacus · mTLS · FastAPI · safetensors · React · Docker Compose.

α/β grid, composition-order and dynamic-vs-static clustering ablations
Privacy sweep ε ∈ {2, 4, 8, ∞} with a membership-inference test
vLLM vs transformers serving ablation
Paper submission and a public reproducibility release (configs, seeds, manifests)

Design targets: time-to-first-token overhead ≤ 200 ms, adapter swap ≤ 2 s, one round ≤ 30 min, registry restore ≤ 10 s, ε ≤ 8 at δ = 1e-5.

Demonstration

Bring up the registry, cluster service and demo UI with one command, or run a full federated round across all four seams.

git clone https://github.com/deeepak-17/CLASP && cd CLASP
docker compose --profile demo up --build      # registry :8004, cluster :8002, demo UI :8010

python scripts/run_services.py --background   # or run the services on the host
python scripts/demo_round.py --round 1        # one round: upload, aggregate, publish, pull, promote

curl -s localhost:8004/adapters/cluster-web/versions | python -m json.tool
curl -s localhost:8004/adapters/cluster-web/promotions
