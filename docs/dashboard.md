# CLASP-P5 · Evaluation Dashboard

Week 5 deliverable: a React + Recharts dashboard, wired to the static `evaluation/results/results.json` Weeks 3/4 already produce. Lives at `dashboard/` (a new, self-contained frontend — none existed in this repository before Week 5; nothing here touches the Python pipeline's logic).

## 1. Purpose

Answer, for a panel or a teammate looking at CLASP for the first time, exactly what P5's Overview page states: what CLASP is evaluating, which benchmarks, what model/run produced the numbers, and — the mandatory distinction — whether those numbers are a real measurement or placeholder/demo data. It is a **read-only viewer** over an existing artefact, not a new evaluation system, not a backend, not a production deployment.

## 2. Dashboard structure

Four pages, a fixed sidebar, matching the Week-5 brief exactly (no extra pages added):

| Page | Route | Answers |
|---|---|---|
| Overview | `/` | What is CLASP evaluating, which benchmarks, what run, REAL vs DEMO, headline Pass@1/Pass@10/tasks/samples |
| Benchmarks | `/benchmarks` | HumanEval and MBPP, one panel each: tasks, Pass@k per k, dataset split, provenance |
| Pass@k | `/pass-at-k` | The Pass@k formula + a grouped bar chart, k on the x-axis, rate on the y-axis, one bar-series per benchmark |
| Evaluation Pipeline | `/pipeline` | Static Dataset → … → Dashboard diagram, terms matching the repository's own module names |

## 3. Data flow

```
evaluation/results/results.json         (Python — evaluation/results_store.py)
        |
        |  scripts/sync-results.mjs      (plain file copy, no transform)
        v
dashboard/public/data/results.json
        |
        |  fetch() at runtime            (dashboard/src/lib/loadResults.ts)
        v
ResultsIndex                              (typed + runtime-validated)
        |
        v
React state (useResults hook)  ->  page components  ->  Recharts (Pass@k page)
```

No backend, no API route, no database. `results.json` is fetched as a static file the same way any static asset would be; the only "server" in development is Vite's own dev server, and in production this is a set of static files (`dashboard/dist/`) that could be served from anywhere (a CDN, a static host, `python -m http.server`).

## 4. results.json usage

`dashboard/src/lib/types.ts` mirrors the Python schema field-for-field (`interfaces/contracts.py::EvalResult`, `evaluation/results_store.py::ResultRecord`/`ResultsIndex`) — nothing is renamed or reshaped between Python and TypeScript. `dashboard/src/lib/loadResults.ts`:

- fetches `/data/results.json`;
- runtime-validates the parsed JSON against the expected shape (`isResultsIndex` and friends) — a hand-edited or truncated file produces a typed error state, not a crash;
- exposes `formatPercent`/`formatOrNA` helpers that render **`N/A`** for any missing field, never a fabricated number;
- exposes `isAllReal`, used to decide whether the DEMO/PLACEHOLDER banner shows.

`npm run sync-data` (also run automatically before `dev`/`build` via `predev`/`prebuild`) copies the repository's real `evaluation/results/results.json` into `dashboard/public/data/`. Python remains the single source of truth; the dashboard never computes or edits a result.

│   │   ├── PassAtKChart.tsx     the one Recharts chart
│   │   ├── PipelineDiagram.tsx  static evaluation-pipeline explainer

│   ├── pages/                 Overview.tsx, Benchmarks.tsx, PassAtK.tsx, Pipeline.tsx
│   ├── App.tsx                 route table

Vite + React 18 + TypeScript (strict mode) + `react-router-dom`. No state-management library, no CSS framework, no UI kit — the surface area is small enough that plain `useState`/`useEffect` and hand-written CSS custom properties are the right amount of machinery.

## 6. Recharts usage

One chart: a grouped `BarChart` on the Pass@k page (`PassAtKChart.tsx`), x-axis = k (categorical: whichever k values are actually present in `results.json`, no assumed fixed set), y-axis = Pass@k rate as a percentage, one bar series per benchmark. A bar chart was chosen deliberately over a line chart: with only one or two discrete k values, a line would draw a slope across the gap that implies a trend the data doesn't contain. Styling follows the restrained, information-dense mark specs used throughout the app — thin capped bars, hairline gridlines, a legend (mandatory for 2+ series), direct value labels, no dual axis, no decorative elements.

## 7. REAL vs PLACEHOLDER

Every `ResultRecord` in `results.json` carries `run_metadata.provenance`: `"REAL"` or `"DEMO_TEST"` (see `evaluation/results_store.py`). The dashboard:

- shows a `REAL EVALUATION` or `DEMO / PLACEHOLDER DATA` badge on every result, on Overview, Benchmarks and Pass@k;
- shows a page-level banner on Overview whenever **any** result is not REAL;
- never blends the two into one unlabelled number.

As of Week 5, every record currently in `results.json` is `DEMO_TEST` (P1's real merged model is not available in this environment — see `docs/eval_harness.md`), so the dashboard currently displays the DEMO/PLACEHOLDER state throughout. This is expected and correct, not a bug: the dashboard is not making up a REAL result that doesn't exist.

The dashboard also explicitly does **not** display the canonical-solution sanity-check numbers (`scripts/sanity_check_scoring.py`, 164/164 and 392/392 = Pass@1 1.0000) as if they were Pass@k for a model — that would misrepresent a pipeline self-test as a capability measurement. The Benchmarks page has a note explaining the distinction instead.

## 8. How to run

```bash
cd dashboard
npm install          # one-time
npm run dev          # dev server with hot reload, http://localhost:5173
npm run build         # type-checks (tsc -b) then produces dashboard/dist/
npm run preview       # serves the production build locally
npm run sync-data     # re-copy results.json from the repo without a full dev/build
```

`sync-data` runs automatically before `dev`/`build`; run it manually after re-running `python scripts/run_baseline_eval.py` to pick up a new result without restarting the dev server (a page refresh is enough — the loader fetches fresh on every mount).

## 9. Current limitations

- Every result currently available is `DEMO_TEST` — the dashboard has not been visually exercised against a `REAL` record because none exists yet in this repository. The REAL-path styling (`badge-real`, the absence of the demo banner) is implemented and covered by the same components, but its first real-world exercise is P1's real merged-model run.
- Single, static snapshot of `results.json` per page load — no live/streaming updates, no polling, no websocket. Consistent with the Week-5 brief ("static results.json (placeholder data)"); live updates are out of this week's scope.
- No historical trend view across multiple runs. `results.json` already supports multiple records (keyed by run_id + benchmark, see `evaluation/results_store.py::append_results`), but Week 5 wires the *current* snapshot only — a trend chart is future scope, not attempted here.
- No automated frontend test suite (no Jest/Vitest component tests). Verification for Week 5 was: TypeScript strict-mode compiles clean, the production build succeeds, and the built app was checked in a real browser (see the Week-5 final report for exact steps and results) — reasonable for a Week-5 skeleton, not a substitute for a dashboard test suite if this becomes long-lived.
